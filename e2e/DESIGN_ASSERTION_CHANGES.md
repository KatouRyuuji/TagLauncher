# 有意设计变更导致的断言更新（ui-redesign）

本文件记录因选定方案落地而必须更新的测试断言。未 skip / xfail。除下方第 6 条经用户确认的 5k 查询上限外，未放宽其它性能阈值。

## 1. 边缘把手：8px 细条 → 探头（68×148）

- **原因**：用户选定「探头」方案。休息态 68×148 逻辑像素，悬停卡片加宽到 168（仍不打开抽屉），顶与展开抽屉对齐。TME_HOVER 120ms 或点击才滑出。
- **单元测试** `src-tauri/src/pin.rs` `sizes_follow_dpi`：
  - `handle_width(1.0)` 8 → 68；`(1.5)` 12 → 102；`(0.5)` 4 → 34
  - 新增 `handle_height(1.0) == 148`、`handle_hover_width(1.0) == 168`
  - 新增 `peek_rect` 与同 offset 展开抽屉顶对齐、右缘贴边
- **E2E** `e2e/tests/desktop/test_desktop_pin.py` `collapsed()`：
  - 原：`6 <= width <= round(8 * scale) + 2`
  - 现：`round(68 * scale) ± 4`（取整容差，非放宽）
  - 只在鼠标已离开（`park_mouse`）后断言休息宽度；悬停加宽 168 不计入 collapsed
- **E2E** `e2e/tests/ui/test_pin.py` E-PIN-04：
  - 宽度同上 `round(68 * scale) ± 4`
  - 新增高度 `round(148 * scale) ± 4`
  - 展开仍为面板宽 320（不变）

## 2. 抽屉滑出动画 84ms → 240ms

- **原因**：与前端 `--transition-normal`（240ms）统一。
- **代码**：`ANIM_STEP` 14ms → 40ms（仍 6 步）。E2E 等待上限 3s，不改阈值。

## 5. 未改动的性能阈值

## 6. 快速窗 5k 搜索 p95：30ms → 35ms

- **原因**：镜面毛玻璃（Windows 亚克力 + 顶栏 CSS `backdrop-filter`）在查询热路径上约增加 4ms。同 runner 对照中 PR #66（4d27d45）正式构建 5k p95 为 29.6ms，距 30ms 仅约 0.4ms 余量。本 PR 多轮绘制优化后，正式约 29.9–31.3ms、debug 约 32.9–34.9ms，稳定落在这条窄带上。2026-11-13 用户明确选择保持镜面，只把 5k 上限调到 35ms。不实施输入期间停模糊、列表改不透明、或去掉玻璃。
- **E2E** `e2e/tests/ui/test_quick.py`：`QUERY_P95_MS[5000]` 30 → 35；模块说明同步。
- **用例表** `e2e/cases.json` E-PERF-QUICK：`输入到出结果 p95 5k≤35ms`。
- 50k 查询 100ms、唤出 80/150ms、隐藏内存、空闲 CPU、主窗滚动等其它上限均不改。

## 7. 质量打磨（t53u）：玻璃可见、截断、探头可读、收纳芯片与清单预览

- **原因**：走查录屏里探头是不可读白块、镜面读成实心白卡片、长标签不截断、钉住顶条与图标不统一、收纳两条就出滚动条。用户要求继续分析打磨，选定方案不变（镜面 / 先选动作 / 清单预览 / 探头）。
- **令牌**：`--glass-bg` / `--glass-bg-strong` 降低不透明度并带少量强调色；浅色 `--glass-border` 改用 `--text-primary` 低透明（不再用近白 `--text-invert`）。键数仍为 139，无新变量。
- **探头**（`pin_strip.rs`）：ClearType 改为抗锯齿、对比不足时换默认正文色、`CS_DROPSHADOW`、亚克力 alpha 0xC0→0x88、回退分层 92%→80%。尺寸仍是 68×148 / 悬停 168，E2E 宽度高度断言不改。
- **视觉基线**：快速窗（更透的玻璃、标签省略、脚注 kbd）、收纳页（文件芯片、动作卡图标与「推荐」徽章）、钉住浮动窗 / 抽屉（细顶线、标题与数量并列、统一线框图标）会与上一轮不同。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：5k 查询 35ms 及其它上限均不改；查询热路径仍暂停亚克力与 CSS 滤镜；新增噪点是静态 repeating 渐变，不含滤镜。

## 8. 探头把手放弃亚克力，改用分层实底（t53u 第二轮）

- **原因**：418b968 走查（run 43387161162）里探头仍是近白 68×148 矩形。对比拉伸后能认出「工作」「7 项」和三行文件名，但原图像素亮度 253–255、标准差 0.63——GDI `DrawText` 叠在 `SetWindowCompositionAttribute` 亚克力上几乎不可见。这是合成问题，不是字体或对比函数写错。
- **改动**（`pin_strip.rs`）：不再调用亚克力；始终 `WS_EX_LAYERED` + 铺实底双缓冲 + ClearType（已知底色）+ 约 90% 整体透明 + 三边描边。休息/悬停尺寸仍是 68×148 / 168，E2E 宽高断言不改。
- **性能**：探头是独立原生窗口，不在快速窗查询热路径上；5k 35ms 及其它上限均不改。

## 9. Win11 系统瞬态背景替换旧亚克力（t53u 第三轮·镜面）

- **原因**：95323a8 走查里快速窗在白底主窗上读成浑浊灰卡片——这是旧 `SetWindowCompositionAttribute` / Tauri `Effect::Acrylic` 加上偏灰、掺了强调色的 tint 的典型样子，不是好的玻璃。深色钉住同样发闷。
- **改动**：Windows 11 build ≥ 22621 用 `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW)`，跟随 `DWMWA_USE_IMMERSIVE_DARK_MODE`，圆角与阴影交给合成器（`DWMWCP_ROUND`）。不再调用 `Effect::Acrylic`。内容层改为明亮 tint（浅 `#fafafc` 约 62%、深 `#1c1c20` 约 62%）加 1px 内高光；不支持时用约 92% 干净实底，绝不走浑浊灰，也不再叠 CSS `backdrop-filter`。查询期间不再拆掉系统背景（合成器侧比 CSS 模糊便宜）。键数仍为 139，无新变量。
- **视觉基线**：快速窗、钉住浮动窗 / 抽屉的镜面材质会与 95323a8 不同（更亮、有系统噪点与圆角阴影，不再是灰卡片）。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：5k 查询 35ms 及其它上限均不改；不放宽、不 skip、不按测量开关。需在正式/debug 构建上重测并报告 p95。

## 10. 探头改用 UpdateLayeredWindow（t53u 第三轮·把手）

- **原因**：95323a8 探头文字已可读，但 `SetWindowRgn` 圆角呈台阶、顶边描边错位或断裂、`CS_DROPSHADOW` 在 region 上无效、约 90% 整体透明让桌面图标透过来。
- **改动**（`pin_strip.rs`）：按像素 alpha 的分层窗口，`UpdateLayeredWindow` 上传预乘 BGRA。软件抗锯齿圆角（仅内侧）、边距里的软阴影、1px 描边、DirectWrite 级别的灰度抗锯齿文字（GDI `ANTIALIASED_QUALITY`，不用 ClearType）。卡片本体约 98% 不透明；通透感靠顶部高光。卡片休息/悬停尺寸仍是 68×148 / 168；HWND 在非贴边一侧和上下含 16 逻辑像素阴影边距，贴边一侧边距为 0（仍与工作区齐平）。阴影区 `WM_NCHITTEST` 返回 `HTTRANSPARENT`（点击穿透）。渲染按设备像素（已有的物理矩形 / PerMonitorV2 缩放）。
- **E2E**：`D-PIN-*` 的休息宽度与上下对齐改看 `pin_diag.handleRect`（卡片），不再用 `GetWindowRect` 的 HWND 宽高——HWND 现在比卡片大，卡片尺寸断言本身不变（E-PIN-04 本就用 handleRect）。
- **性能**：探头是独立原生窗口，不在快速窗查询热路径上；5k 35ms 及其它上限均不改。

## 11. 探头文字对比、更淡阴影、去掉贴边发丝（t53u 第四轮·把手）

- **原因**：94d61e4 走查 4× 里圆角与阴影已对，但灰度 AA 在 12px 上发细发灰（「7 项」和三行文件名对比不足），阴影峰值 0.40、边距 16 对 68px 探头过重，贴边 1px 灰描边在屏幕边缘是发丝。
- **改动**（`pin_strip.rs`）：标题色按 WCAG ≥ 7:1、次要色（「N 项」与文件名行）≥ 4.5:1 且更深；GDI 灰度 AA 在拷入预乘缓冲前按覆盖率做对比度提升（`TEXT_AA_POWER = 1.85`）。阴影边距 16→10 逻辑像素，峰值 alpha 0.40→0.20，仍带轻微 y 偏移。贴边一侧不再画 1px 描边。卡片仍是 68×148 / 168，E2E 继续看 `handleRect`。
- **视觉基线**：探头文字更实、阴影更淡、贴边无发丝。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：探头不在查询热路径；5k 35ms 及其它上限均不改。

## 12. 探头文字改 DirectWrite，字号大半级，文件名行 ≥ 7:1（pt54u）

- **原因**：ef34f2b 走查（v5）4× 里探头标题已实，但「N 项」和三行文件名在 96 DPI 上竖笔只有约 4–6:1，读起来发灰。根因是 GDI `ANTIALIASED_QUALITY` 只能画进不透明临时 DIB，再从颜色里猜覆盖率拷回（`TEXT_AA_POWER` 补偿），不能调 gamma。
- **改动**（`pin_strip.rs` + 新 `handle_text.rs`）：文字改用 DirectWrite，经 Direct2D（WIC 软件目标，`D2D1_ALPHA_MODE_PREMULTIPLIED`）直接画进同一张预乘缓冲。灰度 AA、gamma 1.8、灰度增强对比 1.6、ClearType 级别 0、网格对齐，字体缺失时走系统回退，省略号截断。删掉 GDI 文字路径与 `enhance_aa_pixel` / `TEXT_AA_POWER`（及其单测）。字号 15/12 → 16/13 逻辑像素，按设备缩放取整。文件名行颜色 ≥ 7:1（`contrast_name`），「N 项」仍是 ≥ 4.5:1 的次要色。卡片仍是 68×148 / 168，E2E 继续看 `handleRect`。
- **新单测**：`handle_text_runs` 排版在 1.0/1.25/1.5 下不越出卡片、不重叠；Windows 上离屏渲染浅 / 深色、休息 / 悬停、三种缩放，断言每行峰值对比与实墨像素数、文字不在卡片上打洞、预乘合法，并写出 PNG（`TL_HANDLE_SHOTS_DIR`，缺省系统临时目录）供走查。runner 系统 DPI 固定 96，125/150% 用离屏渲染代替真实系统缩放。
- **视觉基线**：探头文字更大更实。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：探头不在快速窗查询热路径；5k 35ms 及其它上限均不改。

## 13. 浅色快速窗读成玻璃：镜面渐变、亮边、tint 56%（pt54u）

- **原因**：v5 走查里浅色快速窗压在白底主窗上是一块均匀的 (235,235,236) 平卡片，读成磨砂卡，不是玻璃。
- **改动**：`--glass-bg`（浅）#fafafc 62% → 56%，让系统瞬态背景的亮度和噪点多透一点。浅色 + 系统背景时，`::before` 加一层静态竖向渐变：上沿最亮，到约 64% 高度渐透，底部一点回光。`--glass-border`（浅）改成干净的正文色 20% 发丝，不再掺 `border-medium` 的灰。`--glass-highlight`（浅）内亮边 28% → 70%，顶部 1px 镜面线 78% → 95%，新增底部 1px 暗沿（正文色 8%），组成「暗外亮内」的玻璃边。保留原生 `DWMSBT_TRANSIENTWINDOW`，深色不变。键数仍为 139，无新变量。
- **视觉基线**：浅色快速窗与钉住浮动窗 / 抽屉上沿更亮、有渐变和亮边。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：只是静态渐变背景，不用滤镜，不随查询重绘。5k 35ms 及其它上限均不改。

## 14. 快速窗次要文字对比、脚注不换行、深色滚动条（pt54u）

- **原因**：v5 实测里，路径行和标签用 `#626e7c`，在浅色玻璃底（约 232–235）上只有约 4.4:1，选中行（约 221）上约 3.9:1，不到 4.5。深色 125% 下，脚注快捷键把「Esc 收起」挤到了第二行。深色主题的列表滚动条是一根白色系统滚动条。
- **改动**（`quick.css` / `QuickApp.tsx`）：路径、标签、分组标题，以及空结果、收纳说明、钉住计数和预览路径这些压在玻璃上的次要文字，改用 muted 向正文色收三成（`color-mix`，仍只用主题令牌），选中行收近四成，实测底上都 ≥ 5:1。脚注设为容器，窄于 47em 时（100% 字号的 680 宽窗约 53em，全部显示；125% 字号约 42em，收起）收起「Ctrl+Shift+C 复制」和「Alt+Enter 主窗」两个次要提示（完整列表在 title 里），并且不换行。列表用细滚动条，颜色取 `--border-strong`。
- **视觉基线**：快速窗路径行更深，125% 下脚注只占一行，深色滚动条不再是白色。基线不入库。
- **性能**：纯样式；5k 35ms 不改。

## 15. 钉住 / 快速窗列表行：选中是强调色叠色 + 竖条，悬停同色相更轻

- **原因**：76aa205 深色钉住窗里，选中行底是 `accent 16%` 混进 `--glass-bg-strong`（#1c1c20 92%），几乎不透明，读出来是一块无色暗板，看不到强调色，只有左侧竖条在区分。悬停用 `--bg-hover`（不透明纸面色），和玻璃上其它东西不在一层。
- **改动**（`quick.css`，钉住行和快速窗行共用 `.quick-row`）：行底改成强调色向透明混色，直接叠在玻璃上。选中：浅色 16%、深色 18%，加原有竖条。悬停：浅色 6%、深色 8%，同一色相，始终比选中轻；选中行悬停仍显示选中底。选中行次要文字颜色不变，浅色实测底约 (207,210,217) 上路径仍 ≥ 5:1。玻璃本身（tint / 边 / 镜面）不动。
- **视觉基线**：深色选中行带一层蓝灰强调色，不再是暗板；浅色选中行色相不变，略深一点；悬停变成淡强调色。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：纯样式；5k 35ms 不改。

## 16. 探头文件名截断不停在分隔符上

- **原因**：探头休息态只有约 50 物理像素宽的文字区，DirectWrite 字符级裁切会切出「截图 …」「发票-…」这样以空格 / 连字符结尾的省略，读起来像断了一半。
- **改动**（`pin_strip.rs` / `handle_text.rs`）：文字先按 DirectWrite 实测字宽自己挑截断点（`pin_strip::ellipsize`）：取「前缀 + …」能放下的最长前缀，再去掉末尾的 `-` `_` `.` `·` 和空白，然后才加省略号。如果切开的末段只露出 1 个字符（「截图 2…」「已付款.p…」），退到它前面的分隔符之前（前面仍有 ≥2 个有效字符才退；本来就是单字符的完整段不算）。更短的切点只会少留有效字符，所以只要宽度够留 2 个有效字符就会留下。DirectWrite 自带的字符级省略号只作兜底。
- **新单测**：`ellipsize` 纯函数单测（任意平台），覆盖分隔符结尾、连续分隔符、单字符残段、窄到只剩 1 个或 0 个字符的情况，并对一组名字逐个宽度断言放得下、不以分隔符结尾、能留 2 个有效字符时就留。Windows 上用真实字宽在 1.0/1.25/1.5、休息 / 悬停下复查，并写出 `handle-trunc-*.png`。
- **视觉基线**：只影响被截断的文件名行末尾。基线不入库。
- **性能**：每次重绘探头最多 3 行，每行一次二分（约 log₂(名长) 次排版测量），不在查询热路径。

## 17. 空闲 CPU 测量窗口内断开 CDP（harness，1% 上限不变）

- **原因**：空闲 CPU 门在 289a323、530150f 等多个 SHA 上以 1.03–1.15% 失败，735c608 上一度 8–12%。进程级数据只能看到「WebView2 浏览器进程 + 宿主」。
- **诊断**（492568c，新增线程级只读快照：每线程 CPU、上下文切换≈唤醒数、线程名）：
  - PR E2E 43712052582（CDP 挂着）：两个 job 的快速窗隐藏用例都出现**隐藏的渲染进程仍在合成**：renderer `Compositor` ≈2230 次、GPU `VizCompositorThread` ≈2720 次、GPU `Chrome_ChildIOThread` ≈2030 次唤醒 / 120s（约 19 Hz），GPU+renderer 0.26+0.17 s。735c608 那次 8–12% 是同一组线程。
  - 临时分支同一 release 构建对照（Idle diag 43712073932）：CDP 挂着 / 窗口内断开 / 断开且暂停 stealth 轮询，分别为快速窗隐藏 0.49 / 0.61 / 0.47%，浮动窗 0.89 / 0.52 / 0.65%，抽屉收起 0.98 / 0.52 / 0.73%。断开后 GPU 进程唤醒从 ≈5700 降到 ≈75，浏览器 `CrBrowserMain` 从 ≈190ms 降到 ≈30ms（浮动窗）。stealth 守护线程只做只读枚举，暂停它没有可分辨的差别，因此不改。
  - 剩下的浏览器进程开销（`ThreadPoolForeground/BackgroundWorker` 约 0.15–0.2 s，唤醒很少、单次任务长）在三种变体里都在，集中在切换抽屉后的窗口，属于 WebView2 自身的后台任务；`Chrome_DevToolsHandlerThread` ≈430 次唤醒是调试端口本身（需要重启才能去掉，CPU ≈15–45ms）。
- **改动**（`e2e/tests/ui/test_quick.py::measure_idle`，快速窗和钉住视图两个空闲用例共用）：测量窗口开始前 `detach_cdp()`（Playwright `connect_over_cdp` 的 close 只关 websocket，不关 WebView），窗口结束后 `reattach_cdp()` 找回主窗页面（不 reload）。进程树、判定公式、120 s 窗口、10 s 收尾、1% 上限都不变。线程诊断写进 `idle-cpu.json` / `pin-perf.json`（`threads`、`wakeups_by_process`、`cdp_attached`）。`TL_E2E_IDLE_ATTACHED=1` 可恢复挂着的旧口径做对照。
- **为什么不算放宽**：测的是用户机器上的状态（没有调试会话）；挂着 CDP 时多出来的合成与浏览器主线程工作是测试工具造成的，不是产品行为。

## 18. 只有钉住视图在屏幕上时，外部写入检测 100ms → 500ms

- **原因**：线程快照里浮动窗可见时 `tl-data-sync` 每 120 s 约 2200 次唤醒（94–109ms CPU），宿主主线程约 900 次唤醒（另两种状态约 300 次）。原因是钉住视图可见就按主窗口径每 100ms 查一次，而钉住浮动窗设计上可以整天常驻，检测线程永远不降频。
- **改动**（`data_sync.rs` / `pin.rs`）：按屏幕上的窗口选间隔：主窗或快速搜索可见 100ms（主窗 0.3 s 反映目标不变，E-DS-* 不受影响）；只有钉住视图（浮动窗或展开的抽屉）500ms；都不可见 2 s。仅钉住视图时每 5 轮（2.5 s）重新查一次可见性；获焦 / 唤出仍立即检测。
- **视觉基线**：无。
- **性能**：浮动窗常驻时检测唤醒约降到 1/5。

## 19. 收起的抽屉不渲染：合成循环的真正原因是 530150f，回退；保留合成线程唤醒回归检查

- **现象**：693bec8 / 4fdc124（CDP 已在测量窗口断开）抽屉收起的 120 s 窗口内，渲染进程 `Compositor` 约 19 600–23 600 次、GPU `VizCompositorThread` 约 18 100–21 000 次唤醒（约 190 Hz），偶尔浮动窗窗口也出现（6 000–22 000 次）。空闲 CPU 因此 1.04–1.5%。健康时两项都在几十次（最多 389）。`CrRendererMain` 同期只有约 280 次唤醒：页面主线程不在工作。
- **更正**：原先这里写的根因（钉住视图隐藏不调 `SetIsVisible(false)`）是错的。`pin::hide_window` 经 `clear_glass_effect` 早就 `SetIsVisible(false)`，显示经 `native_show` / `apply_glass_effect` 设回 true。据此加的 7bb7783 是冗余的，已回退（d916423）。
- **二分**（临时分支 Idle diag，release 构建，每 job 跑两次钉住空闲用例，CDP 断开；表内为抽屉收起的出循环次数 / 样本数）：
  - 健康：76aa205 0/4、98b4169（选中叠色）0/2、735c608（探头截断）0/2。
  - 出问题：530150f 2/2（其中一次浮动窗也在循环）、96fc4c5 1/2、4fdc124 3/4。
  - CSS 无关：4fdc124 去掉 ca51b3c 细滚动条 1/2、去掉 98b4169 color-mix 叠色 1/2。
  - 回退验证：4fdc124 上回退 530150f + 7bb7783 0/6（43724166373），只把获焦恢复改回无条件 0/4（43726031760）。
- **机理**（43726031760 追踪轮，记录每个 Focused 事件和每次 `SetIsVisible` 回调时的 HWND 状态）：
  - 这条用例里主窗 HWND 始终不可见（`IsWindowVisible=0`，未最小化，未 cloak）。它仍会收到 `Focused(true)`：启动时一次，收托盘后焦点回弹又有 2–3 次，都在 `hide` 后 5 ms 内。
  - 0971b85 原本的写法：获焦时无条件 `SetIsVisible(true)`。收托盘时的 false 随即被撤销，空闲期间主窗 controller 处于「可见」状态，HWND 隐藏，由 Chromium 的遮挡推断处理。实测 0 次循环。
  - 530150f 给获焦恢复加了「HWND 真可见」判断，这些事件都被跳过，主窗 controller 停在 `IsVisible(false)`。此后共享的渲染进程 / GPU 进程间歇进入约 190 Hz 的合成循环（追踪轮 4fdc124 7/8 个样本）。
  - 循环时页面里没有运行中的动画：`document.getAnimations()` 中 running 的为 0。主窗和钉住页面的 `document.visibilityState` 都还是 `visible`。所以循环不是页面内容驱动的，而是 WebView2 / Chromium 在「controller 不可见 + HWND 隐藏」组合下的合成器行为。具体是哪段 Chromium 代码没有定位到。
- **改动**：回退 530150f（3cc9c06），回到 0971b85 的行为：收托盘设 false，获焦恢复 true。
  - 试过的替代方案：按 HWND 真实状态（可见、未最小化、未 cloak）同步主窗 controller，并在隐藏页暂停 CSS 动画。它在 4 个 job 里都让主窗页面停在 `about:blank`，启动失败（43730494755），而且动画假设已被上面的 0 个运行中动画否定，所以没有采用。
- **0971b85 的空闲收益**：收托盘仍调用 `SetIsVisible(false)`。回退后 E2E 各 job 的快速窗隐藏、浮动窗、抽屉收起空闲都在 1% 以下（见本 PR 的 E2E 记录）。
- **回归检查**（`test_pin.py`，`measure_idle` 的 `compositor_wakeups`，4fdc124 加入，不变）：抽屉收起窗口内渲染 `Compositor`、GPU `VizCompositorThread` 各 ≤ 5000 次。这是诊断性断言，防止隐藏页面出帧悄悄回来。1% 空闲上限不变。

## 20. 浅色快速窗真正透出毛玻璃（pt56u）

- **原因**：用户明确要求「半透明毛玻璃效果，优化视觉表现」，不要再在三种外观里选。v5 走查里浅色窗是均匀 (235,235,236) 平卡片；第 13 条把 tint 从 62% 降到 56%、并加上覆盖上半窗的乳状镜面渐变后，76aa205 走查里主体仍是均匀 (233–235) 的灰卡，叠在主窗缩略图上完全看不出背后内容。深色同一套系统瞬态背景能透出彩色缩略图。根因是内容层太厚：`--glass-bg` 56% 近白，再加上 `glass-bg-strong` 60%/34%/12% 的渐变铺在上半窗（顶部等效又叠约 55% 近白），把系统亚克力的色相几乎盖掉；搜索框和钉住预览条还垫了 70–92% 实底。不是要压暗主窗，也不是改成实色。
- **改动**（`shapeLang.ts` / `quick.css`，快速窗与钉住浮动窗 / 抽屉共用）：浅色 `--glass-bg` `#fafafc` 56% → `#ffffff` 36%；`--glass-bg-strong` 改为 `#ffffff` 92%（回退实底仍是干净近白）。浅色 + 系统背景时，`::before` 的镜面渐变改成上沿很快收掉的高光和底部一点回光，不再铺上半窗，也不再叠深色颗粒（合成器自带噪点）。搜索框、钉住预览条、收纳卡片 / 芯片在浅色 + 系统背景下改为半透明玻璃，不再垫近乎不透明的实底。玻璃上次要文字由 muted 向正文收一半（原三成），选中行收到七成，避免更透的玻璃叠上有色背景后对比不足。浅色外阴影略收，避免读成厚卡片。深色 tint 不变，只加一道很淡的上沿高光，和浅色同一套镜面语言。保留原生 `DWMSBT_TRANSIENTWINDOW`，不叠 CSS `backdrop-filter`，不支持时仍用约 92% 干净实底。键数仍为 139，无新变量。
- **视觉基线**：浅色快速窗与钉住浮动窗 / 抽屉会更透、能隐约看到背后内容，上沿是高光而不是乳状罩层；深色几乎不变（多一道很淡的上沿高光）。基线不入库，CI 首次运行 `baseline-created`。
- **性能**：只改静态背景与令牌，不用滤镜，不随查询重绘。不改可见性 / 获焦路径（不重引入 530150f、7bb7783）。5k 35ms、空闲 1%、收起抽屉合成唤醒 ≤ 5000 及其它上限均不改。
